# AGENTS.md

## Назначение файла

Инструкция для AI-ассистентов и разработчиков проекта **Home**: правила кода, структура, конвенции, процесс.
Требования к функциональности и схема БД живут в `README.md` — здесь только «как делать».

**Приоритет источников правды:**

1. Код в репозитории.
2. SQL-миграции в `supabase/migrations/`.
3. `README.md` (требования и логика).
4. Этот файл (правила реализации).

Если документ противоречит коду — прав код, а документ нужно поправить в том же коммите.

**Не поддерживай в документах «таблицы статусов модулей»** — они мгновенно устаревают. Статус = состояние кода и `git log`.

## 3. Соглашения по коду

### 3.1. Общие

- Русский язык — только для пользовательских текстов. Идентификаторы, имена файлов, коммиты — английский/латиница.
- Никаких `any`, `as unknown as`, `@ts-ignore`. Для JSONB — конкретные интерфейсы/типы.
- Файлы ≤ ~400 строк; крупную логику выноси в сервисы/утилиты.
- Один компонент = один файл `.ts` + `.html` (+ `.scss` только при необходимости).
- Чистые функции (расчёты статусов, дат, повторов) — в `shared/utils` или в `<module>/utils/`, без зависимостей от Angular.

### 3.2. Компоненты

- Standalone по умолчанию (`standalone: true` не пишем), `ChangeDetectionStrategy.OnPush` — обязательно.
- Имя файла: `<name>.component.ts` (+ `.html`, `.scss`). Класс: `<Name>Component`.
- Оркестрирующий компонент модуля: `<module>.component.ts` (контейнер + роут), вложенные — в `<module>/components/<name>/`.
- Пиши `input()`, `output()`, `model()`, `viewChild()` (signal-API), а не `@Input()/@Output()` декораторы.
- В шаблонах — `@if`/`@for` (control flow), не `*ngIf`/`*ngFor`. В `@for` всегда `track`.
- Сервисы инжектим через `inject()`, не через конструктор.
- **Не создавай два компонента для одного экрана.** Историческая проблема: `couples.component.ts` + `couples-page.component.ts`, `randomizer.component.ts` + `randomizer-page.component.ts`, `settings.component.ts` + `settings-page.component.ts`. Новый код — только `<module>.component.ts` (контейнер) и `components/*` (части).

### 3.3. Состояние: signals-first

- **Состояние экрана и домена — Angular signals** (`signal`, `computed`, `effect`), не BehaviorSubject.
- **RxJS — только для асинхронных потоков**: HTTP, Supabase-подписки realtime, debounce поиска. Обязательно `takeUntilDestroyed`.
- Внутри одного сервиса не смешивай оба подхода без причины: сигнал — источник правды, Observable — производный поток.
- Загрузка/ошибка — часть сигнального состояния: `loading`, `error`, `data`. Не заводи отдельные boolean-флаги на каждый экран.
- Глобальное состояние (сессия, настройки, тема) — `providedIn: 'root'` сервисы с сигналами.
- `localStorage` — только как кэш для мгновенного старта (тема). Источник правды — БД.

### 3.4. Слой данных

- Каждая сущность БД: `<module>/data/<entity>.service.ts`.
- Все обращения к Supabase — только в `data/`. Компоненты никогда не импортируют `SupabaseService`.
- Сервис возвращает типизированные доменные модели (см. 3.5), а не «сырые» строки Supabase.
- Сигнатура методов: `Promise<T>` для одноразовых операций, `Observable<T>` — если нужен поток. Внутри модуля единообразно.
- Ошибки: сервис логирует и **пробрасывает** ошибку (`throw`), UI-слой показывает `p-toast` с русским текстом. Не глотай ошибки молча.
- Атомарные многошаговые операции (отметка выполнения с пересчётом `next_due_at`, лог истории) — через RPC, а не двумя запросами с клиента.
- После мутации — обновляй затронутые сигналы локально (optimistic update) либо перезапрашивай список; не оставляй UI с устаревшими данными.
- Списки грузим целиком и фильтруем на клиенте (приложение на двух пользователей). Серверная пагинация — только для истории (`*.limit(100)`).

### 3.5. Модели и маппинг БД ↔ TS

- Интерфейс в `models/` описывает **домен** (camelCase), а не колонки БД: `Dish`, `FridgeItem`, `CleaningTask`.
- Соответствие «колонка БД (snake_case) → поле модели (camelCase)» делается **явными функциями-мапперами** в `data/<entity>.mapper.ts`: `mapDishRow(row: DishRow): Dish`.
- `*Row`-интерфейсы (snake_case, ровно как в БД) живут в том же файле маппера и только там используются.
- Никогда не полагайся на «случайное совпадение» имён и не переименовывай поля по вкусу: если в БД `title`, а в модели `name` — это должно быть явно в маппере.
- Даты: из БД приходят строки ISO (`timestamptz`) и `YYYY-MM-DD` (`date`). В модели — `string`; парсинг — в утилитах, не в шаблонах.
- Вычисляемые поля (`status`, `taskCount`, `rating`) — либо `computed` в модели-обёртке, либо поле в доменной модели, заполняемое маппером/утилитой. В БД их нет.
- JSONB-поля типизируем (`RepeatConfig`, `VisibleTab[]`), значения по умолчанию — в маппере.

### 3.6. Стили и дизайн-токены

- Только Tailwind-утилиты. Кастомный CSS — исключение, с комментарием почему.
- Цвета — через токены `@theme` в `src/styles.scss`: `bg-primary`, `text-secondary`, `bg-background` и т.д. **Hex-коды в шаблонах и SCSS запрещены**, кроме preset-файла палитры.
- Палитра: Primary `#C26D55`, Secondary `#8FA18B`, Background `#F9F6F0`, Text `#2D2D2D`. Material-стиль: скругления, тени `shadow-card`, без «неоновых» акцентов.
- Брейкпоинты Tailwind: `sm` 640, `md` 768, `lg` 1024, `xl` 1280. Mobile-first: базовые классы — мобильные, дальше `md:`/`lg:`.
- Иконки — `primeicons` (`pi pi-*`), эмодзи не используем.
- Числовые/датовые форматы — через Angular pipes; локализация `ru-RU` настраивается в `app.config.ts`.

### 3.7. Тема

- Переключение: класс **`.app-dark` на `<html>`** (`darkModeSelector` в PrimeNG-конфиге).
- Единственная точка правды — `ThemeService`: он читает тему из `user_settings` (БД), кэширует в `localStorage` для мгновенной отрисовки и применяет класс.
- `ThemeMode = 'light' | 'dark' | 'system'`; при `system` — `prefers-color-scheme`.
- В компонентах **не трогай** `document.documentElement.classList` напрямую.
- Никаких `dark:` классов для цветов PrimeNG — тему обеспечивает preset; `dark:` допустим для собственных декоративных элементов.

### 3.8. Роутинг и навигация

- Каждый модуль отдаёт `export const routes: Routes` в `<module>.routes.ts`; `app.routes.ts` лениво подключает их через `loadChildren`.
- Все приватные роуты — под `canActivate: [authGuard]`. Меню/навигация строится по этому же признаку.
- `path: ''` ведёт на первый разрешённый пользователю таб, а не на жёстко прописанный `/supplies`.
- После логина — редирект на сохранённый `returnUrl` или на первый видимый таб; после логаута — на `/login`.
- Пункт меню/таб добавляется только вместе с роутом, записью в `VisibleTab` и обновлением настроек.

### 3.9. Формы

- Только `ReactiveFormsModule`, `FormBuilder`, типизированные формы (`NonNullableFormBuilder`).
- Валидация — с русскими сообщениями; сообщение выводится под полем.
- Кнопка сохранения неактивна, пока форма невалидна или не изменена (`pristine`/`dirty`), либо пока идёт сохранение.
- Большие формы — отдельные компоненты `*-form` с `input()`/`output()`, без прямой работы с Supabase.
- Даты — `p-datepicker`/`p-inputnumber`; числовые поля с единицей измерения — `p-inputnumber` + `p-select`.
- Перед отправкой нормализуй данные (trim, пустая строка → `null`, дата → ISO).

## 4. Работа с Supabase

### 4.1. Клиент

- Единственный экземпляр клиента — `SupabaseService` (`core/services/supabase.service.ts`). Не создавай `createClient()` в других местах.
- Ключи — только из `environment.ts`: `supabaseUrl`, `supabaseKey` (publishable/anon). `service_role` на клиенте запрещён.

### 4.2. Авторизация

- Вход по email + паролю (`signInWithPassword`). Регистрация из UI не нужна: два пользователя создаются вручную в Supabase Dashboard, `Enable sign-ups` выключен.
- `AuthService` держит `session`, `currentUser`, `isAuthenticated`, `loading` как сигналы и слушает `onAuthStateChange`.
- Данные профиля — из `profiles` (`full_name`, `avatar_url`); имя показываем в header/sidebar.
- Восстановление пароля — через Dashboard, отдельный экран не делаем.
- При истёкшей/отсутствующей сессии guard отправляет на `/login` с `returnUrl`.

### 4.3. Запросы и RPC

- С фронтенда — только Supabase Client (`from()`, `select()`, `rpc()`), **никакого SQL-текста в TS**.
- Сложные выборки (агрегаты рейтингов, счётчики лайков) — view или `select` с вложенными ресурсами, не N+1.
- Атомарные операции — `rpc()`; список функций описан в `README.md` §8.5. Новую RPC добавляй в миграцию и в README.
- Обязательно проверяй `error` из ответа Supabase до использования `data`.

### 4.4. RLS — принятое решение

Приложение семейное (2 равноправных пользователя), поэтому **осознанно** принято:

- Пользовательские таблицы (`products`, `units`, `dishes`, `fridge`, ...) — полный доступ любому `authenticated`;
- `user_settings`, `push_subscriptions` — только свои строки (`auth.uid() = user_id`);
- `profiles` — чтение всем залогиненным, правка только своей строки.

Не «ужесточай» политики и не добавляй owner-колонки без отдельного решения — это сломает совместные сценарии.

### 4.5. Фото и Storage

- Загрузка — через `shared/components/image-uploader`. Возможен ввод URL.
- По умолчанию файл кладём в Supabase Storage (bucket `photos`, путь `<entity>/<uuid>.<ext>`), в БД храним публичный URL строкой.
- Слой хранилища абстрагирован: конфиг бакета/базового URL — в `environment.ts`, чтобы можно было переехать на внешний CDN.
- Перед загрузкой: проверка типа (image/*) и размера (≤ 5 МБ), сжатие/лимит стороны через canvas при необходимости.

### 4.6. Миграции — обязательное правило

- **Любое изменение схемы** (таблица, колонка, constraint, RLS, функция, триггер) = новый файл
  `supabase/migrations/YYYYMMDDHHMMSS_short_description.sql`.
- Миграция пишется идемпотентно, где это возможно (`if not exists`, `on conflict`), и применяется в Supabase (SQL Editor / CLI) вручную.
- В том же коммите обновляется раздел «Схема БД» в `README.md` (snapshot) — иначе документация расходится с БД.
- Запрещено: менять БД «руками» и не фиксировать это миграцией; удалять колонку без перечисления затронутых сервисов.
- Seed/справочные данные (`units`, `medicine_tags`, значения по умолчанию) — тоже миграцией, идемпотентно.

### 4.7. Push-уведомления

- Подписка создаётся только после явного включения push в настройках и разрешения браузера.
- Хранение: `push_subscriptions` (`endpoint` уникален, `subscription` jsonb), при повторной подписке — upsert по `endpoint`.
- Отправка — Edge Function `send-push` (контракт в `README.md` §10.3). VAPID-ключи и `service_role` — только в Supabase Secrets, не в клиентском коде.
- Клиент ничего не рассылает сам и не знает приватных ключей.
- Протухшие подписки (404/410) удаляются в Edge Function.

## 5. UI/UX-правила

### 5.1. Адаптивность

- Mobile-first. Мобильный: нижний таб-бар (`layout/bottom-nav`), формы на весь экран (`p-dialog` с `[fullScreen]="true"` или отдельный роут), карточки в одну колонку, `pb-20` под таб-бар.
- Десктоп (`md:` и выше): боковое меню (`layout/sidebar`, `ml-64`), модальные окна, карточки в 2–3 колонки (grid).
- Тач-таргеты ≥ 44×44 px; отступы не «слипаются» на 360 px ширины.

### 5.2. Списки

- Поиск и фильтры — вверху экрана, фильтры не сбрасываются при навигации назад в пределах сессии.
- Пустое состояние — общий компонент с иконкой и текстом-подсказкой («Добавьте первый рецепт»).
- Загрузка — скелетоны PrimeNG, не спиннер на весь экран (спиннер — только на старте приложения).
- Сортировка по умолчанию задана в README по модулям; в UI — `p-select`/`p-menu`.
- Карточки — общий компонент модуля, а не копипаста разметки.

### 5.3. Диалоги и фидбек

- Удаление — всегда через `ConfirmDialog` с названием удаляемого объекта; удаление необратимо — текст предупреждает.
- Успешные действия — `p-toast` (`severity: success`), ошибки — `severity: error` с русским текстом. Тост-сервис — один на приложение.
- Долгие операции — блокировка кнопки + индикатор внутри кнопки.
- Формы: закрытие несохранённой формы — подтверждение.

### 5.4. Состояния ошибок

- Ошибка сети/Supabase — понятный текст + кнопка «Повторить», а не пустой экран.
- Офлайн (нет `navigator.onLine`): баннер «Нет подключения» и запрет мутаций с тостом (данные PWA кэширует только на чтение).
- Не логируем в консоль пользовательские данные и токены.

### 5.5. Доступность

- Все интерактивные элементы — кнопки/ссылки, а не `<div (click)>`.
- Иконка без текста ⇒ `aria-label` / `pTooltip`.
- Фокус: диалоги PrimeNG держат focus trap; после закрытия фокус возвращается на инициатора.
- Контраст текста ≥ 4.5:1 (проверяй Primary `#C26D55` на тёмной теме — для текста используй нейтральные токены, Primary — для акцентов/кнопок).
- Изображения — `alt`; состояние (просрочено/мало) дублируется текстом, а не только цветом.

## 6. Логика, которую нельзя изобретать

Расчёты статусов, повторов и дат **заданы** в `README.md` §5. Реализуй ровно по спецификации, не «по интуиции»:

- статусы холодильника (`expired` / `expiring_today` / `expiring_soon` / `ok`);
- статусы уборки и агрегат комнаты, вычисление `next_due_at` (единый алгоритм для `tasks` и `cleaning_tasks`);
- статусы запасов, рейтинг и лайки новинок, вопрос дня.

Если понадобилось отступить от спецификации — сначала обнови README, потом код.

Расчётные функции живут в `shared/utils` (например, `repeat.util.ts`, `status.util.ts`) и покрыты unit-тестами. Дублировать расчёт в двух модулях запрещено.

## 7. Тестирование и качество

- Раннер — **vitest** (`npm test`), тесты рядом с кодом: `*.spec.ts`.
- Обязательно покрываем тестами: расчёт следующей даты повтора, статусы (холодильник/уборка/запасы), мапперы БД↔модель, утилиты дат.
- Компонентные тесты — для сложных форм и списков с фильтрацией (по возможности).
- Схема-генератор `skipTests: true` в `angular.json` — тесты для сервисов/утилит создавай вручную.
- Перед коммитом (заменяет несуществующий `ng lint`):

```
npm run format:check   # форматирование
npm test               # unit-тесты
npm run build          # сборка (production)
```

- Проверяй адаптивность минимум на 360 px и 1280 px.
- Тест считается пройденным только если он реально выполнился; «0 tests run» — не успех.

## 8. Git и процесс

- Рабочая ветка — `main`; изменения — в ветке `feat/<module>-<кратко>` или `fix/<module>-<кратко>`, затем merge.
- Сообщения коммитов — Conventional Commits: `feat(cleaning): таймлайн статусов`, `fix(fridge): учёт quantity_value`, `docs(readme): правила расчёта next_due_at`, `chore(deps): ...`.
- Один коммит = одна логическая правка. Не смешивай форматирование всего проекта с фичей.
